# AI Inference Token Onchain (AITO)

Consumable entitlements to AI inference supply, held and spent on chain.

An AITO unit expresses, under a versioned execution specification, metering rules and delivery conditions, an authorizable and consumable entitlement to AI inference supply. The "token" in the name is the inference token, the unit in which inference usage is counted. It is the denomination of the entitlement, not a blockchain token. Entitlements that meet their transfer conditions are held and circulated through ERC-1155 and ERC-20 tokens.

AITO fixes no price, no conversion rate between suppliers and no ranking of quality. It makes explicit and checkable what is counted, what is promised, who owes it, who may consume it and what was consumed.

## What it defines

- **Five core objects.** Unit (what is counted and how), Grade (what is promised), Source (who issues, who owes supply, on what ground), Instrument (a series: its terms on the ledger and its Terms record, which together say everything a holder is entitled to) and Receipt (what happened to one request).
- **Three optional modules.** Method (typed measurement, calibration and conversion methods), Assessment (who found what under which conditions) and Token Binding (how an entitlement is carried by a token).
- **Series.** Every term that affects a holder's rights is part of the series identifier. A changed term is another series.
- **Consumption.** A holder's authorization is a ceiling. A hold reserves units for one logical request. A settlement deducts what was accepted and releases the rest, once.
- **Bindings.** A native ERC-1155 binding and an ERC-20 wrapper under which no unit can be exercised twice. Wrapped units are unwrapped before they are consumed.
- **Two optional entitlement profiles.** Periodic allowance and reserved capacity, specified with worked state examples.

Out of scope: prices, market making, indices, cash-settled derivatives, proof systems for inference, pooling of several suppliers (see [the design note](docs/redemption-pool-design-note.md)).

| Reserved capacity profile | no, specified only | no |

The ledger has no owner, no upgrade path and no privileged account. It refuses a series that lists a critical extension it does not implement, which includes both optional profiles.

## Build and test

Requires [Foundry](https://github.com/foundry-rs/foundry) (tested with 1.7.1), Node 20 or later and Python 3.

```sh
bash scripts/setup.sh          # fetches forge-std and OpenZeppelin Contracts into lib/
forge test                     # 98 tests: unit, worked cases, fuzz, invariants, vectors
cd tools && npm install && node aito.mjs check && cd ..
python3 tools/profile_examples.py
```

`node tools/aito.mjs check` validates every example record against its schema, recomputes every identifier and confirms that the vectors are what the examples produce. The Solidity tests read the same vectors, including signatures made outside Solidity, so the contracts and the tool are two independent implementations of the identifier, encoding and typed-data rules.

`python3 tools/profile_examples.py` recomputes the two state examples of the optional profiles from their rules. `python3 scripts/make-filing-package.py --check` verifies that the specification quotes the interfaces, the vectors and those tables exactly.

## The two worked cases

**Case A, a supplier's quota.** A supplier issues 1,000,000 units against its own capacity. They are transferred, 200,000 are wrapped into ERC-20, 50,000 change hands in wrapped form and are unwrapped. Their holder authorizes an agent with a ceiling of 20,000. The agent requests at most 4,000; the usage claim of 6,000 input and 2,100 output computes to 3,600; after the objection window 3,600 are deducted and 400 released.

**Case B, an agent issues against its own machine.** An agent is issuer, responsible party and fulfiller, with self-attested evidence that is labelled as such. Another agent holds 200,000 units and authorizes a third to consume up to 50,000. A request for at most 3,000 is claimed at 2,000 input and 1,400 output, which computes to 1,800; the consuming agent accepts by signature; 1,800 are deducted and 1,200 released. A retry has no second effect.

Both are tests (`test/AITOCases.t.sol`) and both are what the evidence run executes on a live network.

## Gas

Measured on a local node, once with the gas rules in force before the Glamsterdam repricing and once with state creation priced at 1,530 gas per byte (EIP-8037, the pricing Sepolia has used since that upgrade).

| Operation | Before the repricing | With state-creation pricing |
| --- | --- | --- |
| Deploy `AITOLedger` | 4,795,982 | 33,980,594 |
| Deploy `AITOWrapper20` | 1,342,555 | 8,663,735 |
| Deploy `AITORecords` | 572,913 | 3,925,289 |
| Anchor a record | 164,600 | 686,200 |
| Create a series (three components) | 661,874 | 3,030,314 |
| Issue | 87,847 | 258,387 |
| Transfer (ERC-1155) | 61,008 | 150,728 |
| Wrap | 111,024 | 376,784 |
| Transfer wrapped (ERC-20) | 51,469 | 140,689 |
| Unwrap | 69,988 | 167,392 |
| Hold | 318,533 | 1,288,665 |
| Claim usage | 148,978 | 501,858 |
| Finalize after the objection window | 161,572 | 530,204 |
| Accept by signature | 170,232 | 539,364 |
| Both worked cases, 33 transactions | 11,305,571 | 65,336,059 |

One request (hold, claim, settlement) is about 630,000 gas before the repricing and about 2,300,000 with it, almost all of it for the record the request leaves on the ledger. The reference implementation favours a complete on-chain trail over a small footprint. The specification allows usage to be settled cumulatively under one request key.
